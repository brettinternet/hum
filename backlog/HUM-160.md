Outcome: when an `http` readiness probe gets a non-2xx response, the diagnostic names the cause, e.g. `status 503: # Phoenix.Ecto.PendingMigrationError at GET /_health/alive`, instead of only `status 503`.

Evidence (2026-11-03): `runNetworkReadinessProbe` in internal/app/app.go closes the response body unread and reports `status %d`. In an enterprise Phoenix setup, readiness failed with `status 503` and the agent had to dig through process output to find the pending-migration error the response body already stated. Go's client sends no `Accept: text/html`, so Plug.Debugger and similar dev error pages return plain text.

Scope: on non-2xx only, read a bounded prefix of the body (on the order of 256 bytes), replace control characters and collapse whitespace to single spaces, trim, and append it as `status NNN: <excerpt>`. Pass the result through the existing `capProbeDiagnostic`. Reading must honor the existing per-attempt context deadline. Successful responses stay unread.

Non-goals: no change to readiness semantics, status-code acceptance, redirect handling, attempt timing, or the manifest schema. No content-type parsing, HTML stripping, or new configuration.
