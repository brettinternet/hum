Problem: after editing `.env`, `.env.local`, or `processes.NAME.env`, `hum up` reports `already running; ready` and the process keeps its launch environment. Nothing tells the user or agent to restart. Edits to argv, cwd, or readiness already surface as `definition_drift` with `hum restart NAME` guidance.

Evidence: docs/design.md "Definition drift" lists environment as not compared, and "Privacy" says "There is no environment hash or drift field." `orchestrate.Ensure` classifies a kept record client-side from a `Get` snapshot (`protocol.Process`, which has no env), so the client cannot see the launch environment. Env files never interpolate (design.md "Environment"), so the manifest's contribution does not depend on the caller's shell.

Design (owner decision 2026-11-17: non-blocking warning; mechanism decided 2026-11-17):
- Fingerprint. internal/project computes a SHA-256 fingerprint of each manifest definition's environment contribution: the `inherit` flag plus the final keys and values set by `environment.files` and `processes.NAME.env`, including `null` removals, in a canonical, versioned encoding. Inherited caller variables are excluded, so a new terminal never reports a change, and CLI and MCP compute the same value for the same manifest. A definition with no environment configuration still gets a fingerprint, so adding `env:` later is detected.
- Transport. Manifest start and restart requests carry a request-only `env_fingerprint`. The daemon keeps it in the in-memory record; automatic relaunch keeps it and an updating restart replaces it. It never appears in responses, runtime state, events, or logs.
- Check. The get request gains an optional `env_fingerprint`. When the record holds a different fingerprint, the process response sets `environment_changed: true`. Records without one (`hum run`, global, retained across a daemon restart, or launched by an older version) never report a change.
- Result. `up` and `start`, in CLI and MCP, set an additive `environment_changed: true` and `hum restart NAME` guidance on any result for a kept record: already running, completed, recovery pending or exhausted, or definition drift. Outcome, exit status, and `after` gating are unchanged. Human progress appends `environment changed; run hum restart NAME`.
- Docs. design.md Definition drift and Privacy record that the fingerprint is request-only and memory-only and that only the boolean is reported; docs/cli-json-v1.md documents `environment_changed`; README's "Changes apply on `hum restart`" mentions the warning.

A fingerprint instead of raw values keeps requests fixed-size, so it cannot push a start request past the request-size limit. A hash in responses was rejected for privacy.

Non-goals: naming changed keys; any fingerprint or hash in responses; reporting in `status` or `list`; watching env files; automatic restart; blocking dependents; persisting fingerprints across daemon restarts.

If the MCP tools/list budget (`TestToolsListBudget`) cannot absorb the schema addition, stop and escalate; never raise the budget to pass.
