Problem: when `up`, `start`, or `restart` reports an early exit or a readiness timeout, the cause is usually in the process's last few output lines, but Hum prints only `inspect retained logs: hum logs NAME`. Humans run a second command; agents spend a second tool call on every failed startup.

Evidence (2026-11-17, built from 024ec7e): a `web` process that wrote `Error: Cannot find module vite` to stderr and exited 1 produced `hum up: web: exited before readiness; inspect retained logs: hum logs web`. A `match` process that logged `warn: DATABASE_URL not set, retrying` timed out with the same bare hint. MCP `up`/`start`/`restart` launch results carry `error` and `guidance` but no output. HUM-160 set the precedent of putting a bounded cause excerpt into failed readiness diagnostics.

Scope (owner decision 2026-11-17: logs entries plus cursor):
- Only for `exited_before_ready`, `timed_out`, and `recovery_exhausted` results, read the final retained entries of the failed launch through the existing stripped, bounded output read: at most 5 entries and 2 KiB of text, both streams, never before that launch's cursor.
- CLI JSON v1 and MCP launch results for `up`, `start`, and `restart` gain one additive optional object, `recent_output`: `session_id`, `entries` (the `hum logs` entry shape: `cursor`, `stream`, `time`, `text`), and `next`, so a client can continue with `logs --after-cursor`. Update the MCP output schemas and docs/cli-json-v1.md.
- Human progress prints the entries indented under the failure line and keeps the `hum logs NAME` hint. Attached `up` already streams output and prints no excerpt.
- Successful launches never read output.

Non-goals: no change to exit codes, readiness semantics, retention, or scheduling; no log parsing or error classification; no excerpt for drift, skips, request errors, or `hum wait` exit 3.

If the MCP tools/list budget (`TestToolsListBudget`) cannot absorb the schema addition, stop and escalate; never raise the budget to pass.
