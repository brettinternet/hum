Problem: when `up`, `start`, or `restart` reports an early exit or a readiness timeout, the cause is usually in the process's last few output lines, but Hum prints only `inspect retained logs: hum logs NAME`. Humans run a second command; agents spend a second tool call on every failed startup.

Evidence (2026-11-17, built from 024ec7e): a `web` process that wrote `Error: Cannot find module vite` to stderr and exited 1 produced `hum up: web: exited before readiness; inspect retained logs: hum logs web`. A `match` process that logged `warn: DATABASE_URL not set, retrying` timed out with the same bare hint. MCP `up`/`start`/`restart` launch results carry `error` and `guidance` but no output. HUM-160 set the precedent of putting a bounded cause excerpt into failed readiness diagnostics.

Leading direction:
- Only for early-exit, readiness-timeout, and recovery-exhausted results, read the final few retained entries (on the order of 5, both streams) through the existing stripped, bounded read path, scoped to the failed launch so an earlier incarnation never appears.
- Human progress prints the excerpt indented under the failure line and keeps the `hum logs NAME` hint. Attached `up` already streams output and prints no excerpt.
- CLI JSON v1 and MCP launch results gain one additive optional field with the entries plus the cursor and session_id needed to continue with `logs --after-cursor`.
- Successful launches never read output.

Non-goals: no change to exit codes, readiness semantics, retention, or scheduling. No log parsing or error classification. No excerpt for drift, skips, or request errors.

Open questions before todo: excerpt size in entries and bytes, and whether it shares the HUM-160 diagnostic cap; field name and shape in CLI JSON v1 and the MCP output schema within the tools/list budget (HUM-126); whether `hum wait` exit-before-match (exit 3) gets the same excerpt.
