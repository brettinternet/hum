Problem: readiness is a startup gate, so `hum status NAME` keeps reporting `ready` after a service starts failing. In an enterprise Phoenix setup a backend became ready, then served 500/503 (pending migrations) while status still said ready; the agent only found out by probing the URL itself.

Leading direction (observation only, no background work), following the 2026-10-10 port-observation precedent:
- Only named status of a running process, through `hum status NAME` and MCP status. Plain list, `list --all`, aggregate status, and internal Get calls never probe.
- Only declared `http` and `tcp` readiness. Never re-run `exec` (status must not spawn subprocesses); `match` and `exit` have nothing to re-check.
- One attempt under a short deadline, run concurrently with port inspection so named status latency stays bounded (about 2s).
- Report a separate additive field, e.g. `probe: {ok, diagnostic, at}`, beside the stored readiness. Never mutate readiness state, emit lifecycle events, or trigger restarts.
- Human output: one compact line, e.g. `probe: status 503: PendingMigrationError ... (now)`.

Requires a decision-001 revision: item 2 says probes "remain startup gates, not liveness monitoring" and item 4 lists liveness/health monitoring as a non-goal. The revision should state that a single caller-initiated probe is observation in the same sense as named-status port inspection, and that continuous monitoring stays out of scope.

Open questions before todo: final field name and shape in CLI JSON v1 and the MCP status output schema; whether the probe and port inspection share one deadline; diagnostics on deadline expiry.

Non-goals: background or periodic probing, liveness-driven restarts, health history, log parsing, probes on aggregate operations, re-running `exec` probes.

Depends on HUM-160 so the probe diagnostic includes the response body excerpt.
