Problem: multi-process `hum logs` prints each process's retained output as a separate block, so correlating one service's error with what the others were doing at that moment means reading timestamps by hand, and human output has no timestamps.

Evidence (2026-11-17, built from 024ec7e): `hum logs --tail 6` in a three-process project printed every `api` entry, then `db`, then `web`. `aggregateLogsRead` (internal/cli/commands.go:1810) reads and renders one name at a time. Every retained entry already carries `time`. `--follow` already prints live output in arrival order.

Outcome: human output for multi-name and no-name `hum logs` without `--follow` prints retained entries in timestamp order with the existing `[NAME]` prefixes (ties by name, then cursor), followed by each name's cursor line.

Non-goals: no global cursor; no change to `--json`, MCP logs, `--follow`, or single-name output; no new flag.

Open questions before todo: whether `--tail N` stays per name (design.md: "Filters, tail, context, and limits apply per name") or applies after merging; how `--match --context` groups render when interleaved; where not-launched and per-name error lines go.
