Outcome: every MCP tool advertises its input as a plain closed object schema that common clients can render, while HUM-064 runtime validation keeps enforcing the same contract.

Evidence (2026-11-03): `objectSchema` in internal/mcp/tools.go adds a top-level `allOf` of `if`/`then` scope rules to every scoped tool, `input` and `remove` add a top-level `oneOf`, and `list` appends a `not`/`anyOf` rule. Several tool-calling clients reject or drop top-level composition keywords; pi's codemode rendered every hum tool's arguments as unknown, so an agent had to guess fields from validation errors and missed `match`, `context`, `no_wait`, and `timeout`. Runtime validation is hand-written and does not read these keys, so removing them loses no enforcement.

Scope: remove top-level composition keywords from every input schema and move each rule into the affected property descriptions:
- scoped tools: project scope requires `project_root`; global scope forbids it (`scope`, `project_root`).
- `input`: exactly one of `text` or `base64`.
- `remove`: `name` or `all: true`, not both.
- `list`: `all` and `port` cannot be combined with global scope.
Update tools_test.go assertions that currently require the `allOf` rules, and docs/coding-agents.md if it describes the schema shape.

Non-goals: no change to runtime validation, error codes, tool results, output schemas (the `remove` output `oneOf` stays), or the daemon protocol. No new tools or fields.
